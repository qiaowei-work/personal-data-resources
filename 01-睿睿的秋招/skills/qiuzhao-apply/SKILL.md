# 秋招投递辅助

## 全流程总览

| 步骤 | 内容 | 状态 |
|-|-|-|
| **1. 岗位检索** | 抓岗位 → 匹配筛选 → 生成《岗位推荐表》 | ✅ 已实现 |
| **2. 建档** | 选定岗位 → 建飞书节点 → 「岗位信息」+「定制简历」 | ✅ 已实现 |
| **3. 填报** | 网申表单填写（本人登录、本人提交） | ✅ 已实现（简历档案；岗位申请表待实测）|
| 4. 回写 | 更新「找呀嘛找工作」Base 的投递进度 | ⏳ 待续写 |
| 5. 增量更新 | 岗位新增/下线时更新推荐表 | ⏳ 待续写 |

**支持从任意一步单独进入。** 每个入口要问哪些输入、依赖哪些前置产物，见下一节。

## 入口：可以从任意一步进入

**五个步骤是一条完整流水线，但支持从中间进入。** 上次会话可能已经做完了前几步，
这次只要接着往下走 —— 常见的是「只要帮我填信息」直接进第三步。

### 铁律：开工前先问齐，再执行

**把该入口需要的输入一次性问完，不要边做边问。**

**Why:** 用户不知道你下一步会要什么，中途反复被打断体验很差；而且缺一个关键输入
（比如没问 base 就开始抓岗位）往往要返工重来。

**How:** 按下面的入口表问齐。**缺任何一项都明确说出来**——"缺这个没法开始"，
不要靠猜、不要先做一半。

| 入口 | 典型说法 | 开工前必须问到 |
|-|-|-|
| **① 岗位检索** | "帮我查 XX 公司的岗位"「搜岗位」 | 公司名 · **目标 base 地** · 秋招官网链接 · 飞书存放位置 · 飞书个人信息库 |
| **② 建档** | "给这个岗位建档" | 要建档的岗位（二级单位 + 岗位名）· 飞书存放位置 · 飞书个人信息库 |
| **③ 网申填报** | "帮我填信息"「填一下这个网申」 | 目标表单链接 · 填哪张表（简历档案 / 某个具体岗位）· 飞书个人信息库 |
| **④ 回写 Base** | "更新投递进度" | 「找呀嘛找工作」Base 链接 · 本次投递的岗位与结果 |
| **⑤ 增量更新** | "XX 公司岗位有更新" | 公司名 · 官网链接 · 已有推荐表节点链接 · 飞书个人信息库 |

**base 地永远要问**（硬规则第 1 条），不得从籍贯、学校、住址推断。

### 从中间进入时，先查前置产物

每个入口都依赖上游产物。**先检查，缺了就补或问用户**，不要带着残缺的前置往下做：

| 入口 | 依赖什么 | 缺了怎么办 |
|-|-|-|
| ② 建档 | 岗位已选定 | 没选定 → 先确认投哪个；**没有推荐表也可以**，让用户直接给岗位名或 JD，或退回第 ① 步 |
| ③ 填报 | 「定制简历」文档存在且已过审 | 没有 → 退回第 ② 步；若本次只填**简历档案**（与具体岗位无关），则只要求飞书个人信息库可达 |
| ④ 回写 | 岗位节点已建 | 没建 → 退回第 ② 步；只想记一行进度 → 直接写 Base |
| ⑤ 更新 | 该公司推荐表节点已存在 | 不存在 → 按第 ① 步从头做 |

### 飞书有两个节点，别搞混

| 输入项 | 作用 |
|-|-|
| 飞书**存放位置** | **产出写到哪** —— 推荐表、岗位节点、简历都在这下面。见「飞书写入位置」 |
| 飞书**个人信息库** | **数据从哪读** —— 建档和填报的取数来源 |

两个是不同的节点。取值见文末「指针」一节；**但每次仍以用户当场给的链接为准。**

## 飞书写入位置

### 存放位置由用户指定

用户提供**一个飞书 Wiki 节点链接**，作为本 Skill 所有产出的父节点。

先解析它：

```bash
lark-cli wiki +node-get --node-token "<用户提供的链接>" --as user --format json
```

从返回中取 `space_id` 和 `node_token`，后续所有建节点操作以该 `node_token` 为父节点。

**不要硬编码 `space_id`。** 用户可能把这一层挪到别处或换一个知识空间，一律以链接为准。

### 目录结构

```
<用户提供的父节点>/
└── <公司名>/                     ← 节点内容 = 该公司《岗位推荐表》
    └── <二级单位>-<岗位名>/        ← 一个岗位一个子节点
        ├── 岗位信息
        └── 定制简历
```

**公司节点本身就是推荐表**，不再单独建「岗位推荐表」子文档 —— 需求是"一个公司一份表"，公司节点 = 这家公司的表，少一层跳转。

用户重命名该节点、或在节点里追加公司概况之类的内容，都不影响结构。若将来确需把推荐表拆成独立文档，在那时再拆即可。

### 为什么岗位要单独一个子节点

1. 岗位后续会长出新东西——笔试记录、面试复盘、HR 联系方式、offer 截图，平铺在两个文档里没地方放
2. 简历是独立文档，导出 PDF 时直接导；若是"长文档里截一段"，导出还得先删掉别的部分

**岗位子节点命名 = `<二级单位全称>-<岗位名>`**，二级单位**必须写全称、不能省、不能用简称**。

例：`中铝乾星（成都）科技有限责任公司-工艺技术主管`

**Why:** 中铝这类集团有几十家子公司，光叫"工程技术"的岗位就有 8 个，不带二级单位完全分不清。
用户明确选择了全称（2026-10-08），即使节点名较长也保持全称——避免简称带来的歧义。

### 节点数量

| 父节点 | 直属子节点 |
|-|-|
| `<用户提供的父节点>/` | = 投递的公司数 |
| `<公司名>/` | = 该公司建档的岗位数 |
| `<岗位名>/` | 2（岗位信息 + 定制简历）|

按 50 家公司、每家建档 3 个岗位估算，最深一层也只有 4 个子节点。**正常使用不会触发上限。**

飞书对单父节点直属子节点数有限制，超限返回 `131003`（该错误码同时覆盖知识空间总节点数和目录深度）。只在单目录下堆积上千节点时才会遇到。真遇到时**不要用相同参数重试**（不是瞬时错误），改为在该层按年份或批次加一级分组。

## 与 Base 的分工（重要）

**会变的东西只在 Base，不会变的东西只在 Wiki。**

| | 归「找呀嘛找工作」Base | 归用户指定的 Wiki 节点 |
|-|-|-|
| 内容 | 投递进度、截止日期、是否已投 | JD 原文、要求拆解、对标分析、定制简历 |
| 性质 | 可变、要排序筛选、要提醒 | 静态、要精读、要反复改 |
| 粒度 | 一行一个岗位（**投过就记，不筛选**）| 一个节点（**只给重点岗位**）|

不要在两边重复记同一件事——Base 里不抄 JD，Wiki 里不记进度。

## 硬规则（不可协商）

### 1. 必须先问 base 地

**绝对不要从籍贯、学校所在地、家庭住址推断 base。**

**Why:** 这类推断几乎必错 —— 实测过一次：按籍贯与学校所在地推出来的 base，被用户明确否掉。
决定 base 的是用户自己的规划，不是他的过去。

**How:** 已知取值见记忆 `qiuzhao-base-city-preference`（该案例也记在那里）。
**即使已知，每次仍应确认一次**（可能变）。

### 2. base 不做硬过滤

用户明确要求：「不希望把 base 定死」。

**Why:** 实测中铝 2027 校招 559 个岗位里，南京 **0** 个、成都 8 个。若按南京硬筛会归零，得出"没有适合岗位"的错误结论。

**How:** 用「base × 适配度」双轴排序。base 命中与异地分开成段，异地单独列出供用户自己判断。

### 3. 输出必须可复核，不能只给结论

每条推荐必须同时给出三样：

- **推荐理由**（逐条对标，写明命中了什么）
- **岗位详情**（JD 原文，不改写、不转述）
- **直达链接**

**Why:** 用户明确要求「除了你帮我做决定，还需要我自己看一下，保证正确性」。只给结论等于让用户盲信。

### 4. 必须交代排除了什么

每份推荐表末尾列出排除数量和主要原因（学历不符 N / 专业不符 N / 职能岗 N / 操作岗 N）。

**禁止静默截断。** 如果只列了 top3，必须写清"共 N 个，此处列前 3"。

### 5. 分档必须读 JD 正文，不能只看字段

**专业字段和类别字段都不可靠**，实测两例：

| 陷阱 | 实例 |
|-|-|
| 专业字段写少 | 「研发工程师｜云南驰宏国际锗业」字段仅"冶金工程类"，JD 正文实为"冶金工程类、**化学类、化工与制药类、材料类**、仪器类" |
| 专业字段占位 | 「教师｜山东铝业」字段写"详见职位描述" |
| 类别字段不可靠 | 全站 83 个岗位类别是"不限职位"，导致「采购工程师」「市场营销管理工程师」等职能岗无法靠类别识别 |

**岗位名也会骗人**：「初级循环再生工程师」JD 实为工程项目管理（招标/施工进度/档案）。

### 6. 简历模板绝对不可修改

生成简历 PDF **必须严格使用** `references/resume-template.tex`，**排版层一个字都不许动**。

**只允许在 `\begin{document}` 之后填内容**。前言层（字体、颜色、间距、宏定义、`\tighten` 开关、CONTENT 标识注释）**原样保留**。

**How:**

```
模板全文  →  从 \begin{document} 处切分
              ├── 之前的部分（前言层）→ 原样复制，不得增删改
              └── 之后的部分（内容层）→ 用岗位定制内容替换
```

**Why:** 格式一致性是硬要求。每次重写排版层会导致不同岗位的简历版式不一致，
投递记录看起来零散；而且排版层的参数是调过的（行距、间距、字体回退），
随手改会破坏版面。

**落地做法**：把内容层单独存成 `content.tex`，`resume.tex` = 模板前言层（逐字节复制）+ `content.tex`。
这样"不改模板"成了结构上的保证，而不是靠自觉。

**组装后必须复核**：前言层与模板**逐字节一致**，不一致就重做。

### 7. 审核范围必须等于渲染范围

**用户审核了什么，PDF 里就只能有什么。反之，PDF 里要有的，用户都必须审过。**

这条在**两头**都成立，缺一头就会出问题：

| 方向 | 违反的后果 |
|-|-|
| PDF 里多了用户没审的 | 用户看到的成品和他批准的版本不一致，而他不自知 |
| PDF 里少了用户审过的 | 审核白做了 |

**落地要求：**

1. 「定制简历」文档 = **完整简历文字稿**（见 Step 5），不是片段。这样"审核范围 = 渲染范围"才可能成立。
2. 渲染前做**逐条对照**：`content.tex` 每句 ↔ 文档每句，双向核对。
3. **任何从外部来源（旧简历、模板示例、行业惯例）引入的内容，都必须先写进文档、标明来源、让用户过目**，不得在渲染时直接落地。

**Why:** 用户无法审核他看不到的东西。审核的价值完全依赖于"审核的就是最终产物"这个前提。
一旦渲染阶段能自由增删，审核就成了形式。

**实测教训（2026-10-08）**：初版把「定制简历」定义为"选哪几段经历"的**片段**，
渲染时发现简历还缺教育背景、专业技能、荣誉与成果，就从用户旧的通用简历里**直接搬了过来**。
结果：**一半章节从未进入审核**，用户完全不知道。
同时还照抄了模板示例行，多出「成果：论文撰写中」等表述——
而"撰写中"根本不是成果，挂在「成果：」下等于主动告诉 HR「我还没产出」。

**模板示例行是占位符，不是内容。** `XXX`、`课程一（90）`、`成果：论文在投 / 在写 / 已发表`
都只是示意格式，**必须替换成文档里真实存在的内容**。

### 8. 写入飞书后必须校验格式

**飞书的 markdown 解析器不可靠，会静默改变格式 —— 不报错、不警告。**

**实测缺陷（2026-10-08）：相邻加粗会被合并。**

源文件（本地 md）：
```
**招 5 人**（本批次…）；JD 专业要求明确列出"**化学、环境科学与工程、分析检测、材料表征**"等方向
```

写入飞书后实际存储的（XML 导出确认，非渲染假象）：
```
**招 5 人（本批次…）；JD 专业要求明确列出"化学、环境科学与工程、分析检测、材料表征**"等方向
```

**两段独立加粗被合并成一段**，加粗跨度覆盖了中间的普通文字。当时的对比：源文件 100 段加粗，飞书 99 段。

**校验方法**（写完后必须做）：

```bash
lark-cli docs +fetch --doc <node_token> --as user --doc-format xml
# 数源文件的 **...** 对数 与 文档的 <b> 段数，**必须相等**；不等就是被改了
```

**两个 fetch 的坑：**

1. **必须用 `node_token`**（`/wiki/` 链接里的那串），**不要用 `wiki +node-get` 返回的 `obj_token`** —— 实测后者报
   `Invalid document_id or document not found`，而同一个文档用 node_token 取完全正常。
2. **判断是"存储损坏"还是"导出损耗"，必须看 XML。** markdown 导出会做格式归一化，不能作为依据；
   XML 保留真实格式结构。

**修的时候注意**：把被打散的 `**` 再按原样写回去，**会被再次合并** —— 因为合并发生在解析时，不是存储时。
必须**改写结构**（例如该段只保留一处加粗），并把源文件同步改掉，否则下次重新生成会再犯。

**规避**：同一段里避免"加粗 + 普通文字 + 加粗"的结构。宁可少加一处粗，也不要让它被合并。

**Why:** 飞书文档是最终交付物，本地 md 是事实源。格式被静默改动后两者不一致，
而这类改动**没有报错、没有警告**，只能靠主动校验发现。用户会发现"飞书上的不如本地好"。

### 9. 只填不提交

**AI 负责抓取、翻页、填字段；「提交」按钮一律由本人点击。**

**Why:** 网申提交不可撤回，投错岗位、填错字段的代价由用户承担。
且提交是对第三方作出的意思表示，不是可以代劳的操作。

**How:**

- 填完明确告诉用户「已填完，请你核对后自己点提交」，并给出逐条判断留痕
- **不替用户点提交**，也不在用户没明确要求时自动跳到提交页
- 用户已在浏览器登录，Skill 不代登录、不碰账号密码

# 第一步：岗位检索与推荐表

### Step 0 · 前置检查

确认浏览器工具可用（chrome-devtools MCP）。

### 这个 MCP 会频繁瞬时断连 —— 这是正常的

**表现**：工具报 `still connecting` 或 `No such tool available`。

**处理：直接重新调用工具即可。** 通常几次之内就恢复（实测：同一次会话里断连并自行恢复过 3 次以上）。

**不要做的事：**
- ❌ 不要判定为"需要重启 Claude Code"（我曾据此让用户重启，是错的）
- ❌ 不要跑进程诊断、手动探测、写 CDP 脚本兜底 —— **在还有救的情况下这些都是浪费**
- ❌ 不要因为一次失败就切换方案

**唯一需要重启的情况**：反复重试超过约 10 次仍不恢复。此时再考虑重启。

**已知限制**：`evaluate_script` 和 `fill_form` 在部分客户端会被拒（报 "This client cannot show tool-permission prompts"）。
→ 用 `fill`（单字段）替代 `fill_form`，能正常工作。

**兜底：CDP 直连。** 只在 MCP 确实长时间不可用时才用。Chrome 新版把 `http://127.0.0.1:9222/json/*` 全部返回 404，需从 `~/Library/Application Support/Google/Chrome/DevToolsActivePort` 读取端口和 `/devtools/browser/<uuid>` 路径，用 WebSocket 直连。脚本见 `scripts/cdp.mjs`。

**截图注意**：飞书等 SPA 用虚拟滚动渲染，`scrollIntoView` 直接跳转会截到未渲染的空表格。必须**渐进滚动**（每次 600px，间隔 ~900ms）并等 3~4 秒再截。**截图显示空表格不等于内容没写进去——先用 `docs +fetch` 回读内容确认，再判断是渲染问题还是写入问题。**

### Step 1 · 抓取岗位数据

**优先级：找页面自身的 XHR 接口 ≫ DOM 抓取。**

1. 用 `list_network_requests`（resourceTypes: xhr/fetch）观察页面调用了什么接口
2. 若有岗位列表接口，记录请求体结构（页码、分页大小、project_id / company_id 等固定参数）
3. 在页面上下文执行 `fetch`（同源可绕 CORS）分页拉全量
4. 保存原始数据为 JSON，**保留 `contents`（JD 正文）字段**——后续复核必须用

已适配站点见 `references/site-adapters.md`。

若找不到接口，退化为 DOM 抓取；再不行请用户手工粘贴。

### Step 2 · 归一化

统一为：

```
job_id / title / company / sub_company / location / education
majors[] / headcount / deadline / url / jd_text / category / source_site
```

`sub_company`（二级单位）**必须有**——中铝光叫"工程技术"的岗位就有 8 个，不带二级单位分不清。

### Step 3 · 粗筛（字段 ∪ JD 正文，取并集）

纳入判定 = **平台专业字段命中白名单 ∪ JD 正文命中类目关键词**。

必须取并集而非只信字段——理由是硬规则第 5 条的字段缺陷。

同时剔除：
- 学历不符（用户为硕士：排除要求"大专"和"博士"的岗位）
- 一线操作岗（优先用平台 `category` 字段；字段缺失或与岗位名冲突时交模型读 JD 判断。**不要手写工种词表**——实测漏了「铸轧工/熔炼工/装配工/压力加工」）

**学历要求写"本科"的岗位要纳入，但单独标注**（校招里"本科"常含硕士，但需用户确认）。

### Step 4 · 读 JD 复核

对进入推荐范围的岗位读 `jd_text` 正文，判断**岗位实质**：

- 是技术/研发岗，还是其实为项目管理、仓储、销售？
- 职能岗（采购/供应链/市场/销售/人力/财务）即便专业命中也不推荐

**首轮实操教训**：只看字段会把「初级循环再生工程师」（实为工程项目管理）排进高档位。复核不能省。

### Step 5 · 分层排序

**base 命中区**：按优先级 首选 / 次选 / 备选 / 降级 / 不推荐

**异地**：按**专业对口程度**排序，只取 **Top 3**。排序依据见 `references/major-whitelist.md`。

### Step 6 · 生成推荐表

格式见 `references/recommendation-table-format.md`。

1. 先落本地 Markdown 给用户过目
2. 用户确认后，在**用户提供的父节点**下建 `<公司名>` 节点，把推荐表内容写进该节点

**若 `<公司名>` 节点已存在**（之前搜过这家公司），不要新建，**更新该节点内容**，并在表末「变更记录」追加一行。这是第 5 步「增量更新」的基础。

---

### 输出物（第一步）

一份《<公司名>-岗位推荐表.md》，结构：

```
文档信息（目标base / 数据来源 / 生成时间 / 最近更新）
摘要（总数 / 纳入 / base命中 / 异地Top3 / 排除 / 某base为0的警示）
⚠️ 筛选方法及其局限（必读）
复核状态说明
一、base 命中（优先级 / 岗位 / 单位 / 地点 / 学历 / 招 / 截止 / 状态 / 复核 / 推荐理由 / 链接）
二、异地 · Top 3
三、排除说明
四、岗位详情（仅"首选/次选"铺 JD 原文）
五、变更记录
```

**复核状态三档**：`✅ 已读JD·推荐` / `❌ 已读JD·不推荐` / `⏳ 未复核`

# 第二步：建档

## 触发

用户在推荐表里选定岗位后（通常是「首选/次选」，也可能包含「备选」）。

**不是每个投递岗位都建档。** 只给用户明确要投的重点岗位建；其余只进 Base 记一行即可。

> **本步是常见的单独入口** —— 用户可能上次已查完岗位，这次直接说「给这个岗位建档」。
> 开工前按「入口」一节问齐输入、查完前置产物，再动手。

### Step 1 · 确认前置

- 公司节点 `<用户提供的父节点>/<公司名>/` 是否存在？第 1 步应该已经建了；不存在则先建：

```bash
lark-cli wiki +node-create --parent-node-token <父节点 node_token> --title "<公司名>"
```

- 推荐表内容是否已写入该公司节点？

### Step 2 · 建岗位子节点

```bash
lark-cli wiki +node-create \
  --parent-node-token <公司节点 node_token> \
  --title "<二级单位>-<岗位名>"
```

命名见「飞书写入位置」一节。**二级单位不能省。**

### Step 3 · 建两份文档

在岗位子节点下，依次建：

```bash
lark-cli wiki +node-create --parent-node-token <岗位节点 node_token> --title "岗位信息"
lark-cli wiki +node-create --parent-node-token <岗位节点 node_token> --title "定制简历"
```

模板见 `references/doc-templates.md`。

### Step 4 · 填充「岗位信息」

数据来源：第 1 步抓取的原始 JSON（含 `jd_text`）。

- **JD 原文原样粘贴**，不改写、不转述
- **硬性条件对标逐条做**，不确定的标 ⚠️，不要猜
- 加分项没有的写"无"，**不要编**

### Step 5 · 起草「定制简历」（**完整简历文字稿**）

**个人信息全部来自飞书个人信息库**，实时读取，不用缓存。节点位置见「输入」。

**产出是简历全文，不是片段。** 必须包含页眉、教育背景、科研经历、项目经历、学生工作、
专业技能、荣誉与成果 —— **简历 PDF 里会出现的一切**。

**Why:** 用户审核的是这份文档，审核范围必须等于渲染范围。
初版把它定义成"选哪几段经历"的片段，结果渲染时简历还缺教育背景/专业技能/荣誉等章节，
就从用户旧的通用简历**直接搬了过来，既没标注也没让用户过目** —— 产出的 PDF 里
一半章节从未进入审核。这不是用户审得不仔细，是给他的审核范围本身残缺。

**只做「选择 + 改写」，不新增事实。** 四条硬约束：

1. 改写过的条目，在文末「改写对照表」列出 **原文 / 改写后 / 改写理由**
2. 文末「来源说明」逐条列明每章来源；**从旧简历、模板示例或任何外部来源搬来的内容，
   必须逐条列明并标 ⚠️**，让用户决定是否重新确认 —— 不得默认沿用而不告知
3. **模板示例行是占位符，不是内容**（如 `成果：论文在投 / 在写 / 已发表`）——
   不得照抄，不得据此补充
4. 通过零编造校验：正文里所有数字和专有名词都必须能在知识库找到出处

细则见 `references/doc-templates.md`。

### Step 6 · 交付用户审核

把两份文档的链接给用户，**明确说明**：

- 哪些内容是原文照搬，哪些是改写
- 有哪些判定标了 ⚠️ 需要其打电话确认
- 有哪些字段因知识库缺失而留空

**用户审核通过后，才进入渲染。** 不要自行认为已经完工。

### Step 7 · 渲染简历 PDF（用户审核通过后才做）

**顺序不可颠倒**：先审文字、再审版式。文字改一行是拖一下，PDF 改一行要重编译一遍。

**模板绝对不可修改**（见硬规则第 6 条）。做法：

```
1. 对照校验：content.tex 的每一句 ↔ 已审核的「定制简历」文档的每一句
   —— 双向都要对得上，不多不少。对不上就停止，先回去修文档并重新让用户审
2. 建岗位目录：简历/<二级单位全称>-<岗位名>/
3. 写内容层 → content.tex（自 \begin{document} 起，至 \end{document}）
4. 复制 photo.jpg（用 tex-template/ 下已调好尺寸的那份，非原始证件照）
5. 组装 resume.tex = 模板前言层（逐字节复制，到 \begin{document} 之前）+ content.tex
6. 复核：前言层与模板逐字节一致，不一致重做
7. 编译两遍：xelatex resume.tex
8. 跑模板要求的必查两项：
   - 缺字：grep -i "missing character" resume.log   → 必须无输出
   - 页数：pdfinfo resume.pdf | grep Pages          → 必须为 1
9. 转图目视确认：pdftoppm -png -r 130 resume.pdf page && 看图
10. 把 PDF 作为附件挂到飞书「定制简历」节点下
```

**第 1 步是新增的强制关卡，不可跳过。** 它是防止"渲染时顺手加内容"的唯一机械保障 ——
靠自觉没用，实测已经出过一次。

**第 10 步上传的两个坑（都实测踩过）：**

1. **替换已有 PDF 时，`--file-token` 原地覆盖会连文件名一起改掉。** 必须显式带 `--name`：

```bash
# 首次上传
lark-cli drive +upload --file resume.pdf --wiki-token <节点> --name "<姓名>-<岗位>-简历.pdf"

# 替换已有文件（原地覆盖，保留原链接）
lark-cli drive +upload --file resume.pdf --file-token <file_token> --name "<姓名>-<岗位>-简历.pdf"
```

漏了 `--name`，文件名会变成 `resume.pdf` —— **这个文件名是要跟着简历提交给 HR 的**，必须用 `姓名-岗位-简历.pdf` 格式。
补救：`lark-cli drive +update-title --url "<wiki链接>" --title "<正确文件名>"`。

2. **模板变更后重渲染，只需重做第 2~10 步，`content.tex` 不用动。**

**前提是模板只改了排版层。** 所以拿到新模板先做一次前言层 diff：

```bash
# 对比新模板前言层 与 上次用的前言层
diff <(sed -n '1,/\\begin{document}/p' 新模板) <(sed -n '1,/\\begin{document}/p' 旧resume.tex)
```

- **只有排版层变化** → 直接用新前言层重新组装，内容层不变，**无需重新让用户审核**（内容没变）
- **宏名 / 内容层接口变了**（如 `\skillrow` 改名、参数个数变了）→ **必须改 `content.tex`**，且改动属于内容变更，**要重新走 Step 6 审核**

实测（2026-10-08）：模板改动是删掉页眉下的横线 + 调整间距，宏接口完全未变，因此只重新组装即可。

**超页处理**：先在内容层开头去掉 `% \tighten` 的注释（模板已备好压缩开关）；
仍超则**删条目，不要动排版层**。

**希腊字母必须走数学模式**（`$\delta$`、`$\mu$`），否则拉丁字体无此字形，PDF 会显示空白但复制文字正常 —— 极易漏检。

# 第三步：网申表单填报

**红线：AI 只负责填，提交一律由本人点击**（硬规则第 9 条）。

技术手册见 `references/form-filling.md`。本节只讲流程。

> **本步是最常被单独调用的入口** —— 用户经常直接说「帮我填信息」。
> 开工前按「入口」一节问齐输入（**表单链接 · 填哪张表 · 飞书个人信息库**），再动手。

### Step 1 · 确认前置

- 浏览器 MCP 可用（断连处理见第一步的 Step 0）
- **用户已在浏览器里登录目标站点**
- 目标岗位已建档（第二步）；若本次是填「简历档案」，只要求「定制简历」文档已通过审核
- 明确本次填的是哪张表：**简历档案**（个人中心，一次性）还是**岗位申请表**（投一个填一次）

### Step 2 · 从飞书取个人信息

**个人信息全部来自飞书个人信息库，实时读取，不用缓存。** 节点位置见「输入」。

若该库里有一页是**按表单字段组织的对照页**（如「填表速查卡」），**优先用它** ——
它通常就是为这一步准备的。

飞书里没有的字段：先查该库自带的「待补充清单」之类；仍没有 → **停下来问本人**，
**不得用行业惯例补**。必填又拿不到数据的处理原则见 `references/form-filling.md` §4.2。

### Step 3 · 逐板块填报

按站点给出的板块顺序，**填一个保存一个**，不要攒着。

通用手法（受控组件、级联弹窗、文件上传、保存按钮）见 `references/form-filling.md`，
站点特有结构见 `references/site-adapters.md` 的「表单填写」小节。

### Step 4 · 验证

保存后确认编辑器关闭且无字段报错；**全部填完 reload 回读**，核对完成度标记（如国聘的「简历目录」）。

**只信回读，不信「点了保存」** —— 实测中保存过一次没生效，靠刷新才发现。

### Step 5 · 交付用户复核

列出**逐条判断留痕**：

- 哪些字段平台没有对应选项，取了最接近的哪个
- 哪些字段是单选，只能取一个（如城市）
- 哪些必填字段知识库缺数据，用了什么值（如税前月薪填 0）
- 哪些板块因选项不匹配而未填

### Step 6 · 本人提交

**走到这一步 Skill 就停手。** 提交按钮由用户自己点。

提交完成后可回写 Base 投递进度（第四步）。
