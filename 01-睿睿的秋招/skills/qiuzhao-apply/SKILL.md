# 秋招投递辅助

## 全流程总览

| 步骤 | 内容 | 状态 |
|-|-|-|
| **1. 岗位检索** | 抓岗位 → 匹配筛选 → 生成《岗位推荐表》 | ✅ 已实现 |
| **2. 建档** | 选定岗位 → 建飞书节点 → 「岗位信息」+「定制简历」 | ✅ 已实现 |
| **3. 填报** | 网申表单填写（本人登录、本人提交） | ✅ 已实现（简历档案；岗位申请表待实测）|
| 4. 回写 | 更新「简历投递记录」Base 的投递进度 | ✅ 见入口 ⑥ Step 7 |
| 5. 增量更新 | 岗位新增/下线时更新推荐表 | ♻️ 复用第①步：更新已有公司节点 |

**入口 ④ 没有独立流程**（= 入口 ⑥ Step 1 定位记录 + Step 7 回写）；**入口 ⑤ 复用第①步**，只是公司节点已存在时改为更新。
**入口 ⑥「按记录投递」= ② + ③ + ④ 的编排** —— 你报公司名/二级单位名，AI 从 Base 取对应记录，一路推到「待你点提交」，最常用。

**临时文件**：所有中间产物（快照、抓包 JSON、CDP 脚本、飞书导出、预览图、编译日志）写到系统临时目录
或项目内 `_tmp/`，**任务结束删除**；交付目录只留最终文件，不要在用户目录留 `.tmp-*`。

## 入口：可以从任意一步进入

**五个步骤是一条完整流水线，但支持从中间进入。** 上次会话可能已经做完了前几步，
这次只要接着往下走 —— 常见的是「只要帮我填信息」直接进第三步。

### 铁律：开工前一次问齐，再执行

**把该入口需要的输入一次问完，不要边做边问。缺任何一项都明确说出来**——"缺这个没法开始"，
不要靠猜、不要先做一半。前置产物缺了就补或问用户，不要带着残缺的前置往下做。

**Why:** 中途反复打断体验很差；缺一个关键输入（比如没问 base 就抓岗位）往往要返工。

**例外**：入口 ⑥ 的「方向 A/B」必须先读 Base 记录才能问 —— 先定位记录，**问完方向再动手**。

| 入口 | 典型说法 | 开工前必须问到 | 前置产物 / 缺了怎么办 |
|-|-|-|-|
| **① 岗位检索** | "帮我查 XX 公司的岗位"「搜岗位」 | 公司名 · **目标 base 地** · 秋招官网链接 | — |
| **② 建档** | "给这个岗位建档" | 二级单位 + 岗位名 | 岗位未选定 → 先确认；没有推荐表也可以，直接给岗位名/JD，或退回① |
| **③ 网申填报** | "帮我填信息"「填一下这个网申」 | 表单链接 · 填哪张表（简历档案 / 具体岗位）| 岗位申请表：「定制简历」已过审；简历档案：个人信息库可达 |

## 飞书写入位置

### 存放位置（已写死，可按次覆盖）

**默认父节点 —— 不用问，直接用：**

```
投递公司详情
https://ncnmmj6cf0ef.feishu.cn/wiki/EI5owzKRliqQzKkA26PcyjsUnoh
node_token = EI5owzKRliqQzKkA26PcyjsUnoh
space_id   = 7691736929070500814
```

**例外**：用户**明确说这次写到别处**时才覆盖，用他给的链接；不要拒回默认值。

**用 `node_token`，不要用节点名** —— 名字会变，token 不变。

解析方式（确认节点还在、拿 space_id）：

```bash
lark-cli wiki +node-get --node-token "EI5owzKRliqQzKkA26PcyjsUnoh" --as user --format json
```

从返回中取 `space_id` 和 `node_token`，后续所有建节点操作以该 `node_token` 为父节点。

### 目录结构

```
投递公司详情/                     ← EI5owzKRliqQzKkA26PcyjsUnoh（写死）
└── <公司名>/                     ← 节点内容 = 该公司《岗位推荐表》
    ├── <二级单位>-<岗位名>/        ← 一个岗位一个子节点
    │   ├── 岗位信息
    │   └── 定制简历
    └── <二级单位>-<另一个岗位>/     ← 同一家公司投多个岗位时并列
        ├── 岗位信息
        └── 定制简历
```

**公司节点本身就是该公司的推荐表**，不再单独建「岗位推荐表」子文档。
**岗位单独一个子节点**：后续笔试/面试/HR/offer 有地方放，简历也能独立导出。

**岗位子节点命名 = `<二级单位全称>-<岗位名>`**，二级单位**必须写全称、不能省、不能用简称**。
例：`XX（城市名）科技有限责任公司-工艺技术主管` —— 括号里的地名也是全称的一部分。

**Why:** 集团子公司多，光叫"工程技术"的岗位就有 8 个，不带二级单位完全分不清。

### 节点数量

正常规模远低于飞书上限：50 家公司、每家 3 个岗位，单目录最多 50 个子节点。
若真的返回 `131003`（单目录节点过多 / 层级过深）：**不要用相同参数重试**，在该层按年份或批次加一级分组。

## 与 Base 的分工（重要）

### 投递记录 Base（已写死）

```
简历投递记录（多维表格）
https://ncnmmj6cf0ef.feishu.cn/wiki/Ec98wjsfuifnEgk1gtbcbiWMn0c
base_token = EGkqbFQmkauCe4sqdJOcKmWon4T
table_id   = tblPKAEr1fsJ3oSm     （表名：投递记录）
```

**这张表是「待投队列」，不只是记账。** 用户报公司名/二级单位名，Skill 从里面取对应记录去投。

字段：`岗位名称 / 公司 / 城市 / 公司类型 / 优先级 / 投递状态 / 投递日期 / 截止日期 / 岗位链接 / 建档节点 / 备注`

> **`岗位名称` 是投递完成后才写的字段**：投递前留空；用户确认「已提交」后，写入**最终实际投递的岗位名称**（见 Step 7）。投递前指代岗位时，用 `岗位链接` 或 `备注`，不要预填 `岗位名称`。

读写命令：

```bash
# 按公司名找记录（--search-field 必填；--field-id 只取需要的列）
lark-cli base +record-search --base-token EGkqbFQmkauCe4sqdJOcKmWon4T --table-id tblPKAEr1fsJ3oSm --as user \
  --keyword "<公司名或二级单位名>" --search-field "公司" --search-field "岗位名称" --search-field "备注" \
  --field-id "公司" --field-id "岗位名称" --field-id "投递状态" --field-id "截止日期" \
  --field-id "岗位链接" --field-id "建档节点" --field-id "备注" \
  --limit 50 --format json

# 读全部（含 record_id）
lark-cli base +record-list --base-token EGkqbFQmkauCe4sqdJOcKmWon4T --table-id tblPKAEr1fsJ3oSm --as user

# 回写（按 record_id；`岗位名称` 仅在用户确认提交后写入）
lark-cli base +record-batch-update --base-token ... --table-id ... --as user --json \
  '{"update_records":{"rec...":{"投递状态":["已投"],"投递日期":"<YYYY-MM-DD>","岗位名称":"<最终实际投递的岗位名称>"}}}'
```

**`+record-list` 只在内部核对时用，不要贴给用户当选择菜单。**

**进度和状态只在 Base，岗位内容只在 Wiki。**

- Base 记**进度/状态**：投递进度、截止日期、是否已投；一行一个岗位，**投过就记，不筛选**；`岗位名称` 投递完成后再回填，投递前留空
- Wiki 记**岗位内容**：JD 原文、要求拆解、对标分析、定制简历；**只给重点岗位**建节点
- 两边不重复：Base 不抄 JD，Wiki 不记进度

## 硬规则（不可协商）

### 1. 检索岗位必须先问 base 地

**只对检索类入口生效**：① 岗位检索、⑤ 增量更新、⑥-B 重新搜集。
已锁定具体岗位的 ② 建档、③ 填报、⑥-A 直接投，**不再问 base**（岗位已经定了）。

**绝对不要从籍贯、学校所在地、家庭住址推断 base。**
**Why:** 这类推断几乎必错 —— 实测按籍贯与学校推出来的 base，被用户明确否掉。
决定 base 的是用户自己的规划，不是他的过去。
**How:** 已知取值见记忆 `qiuzhao-base-city-preference`；**即使已知也每次确认一次**（可能变）。

### 2. base 不做硬过滤

用户明确要求：「不希望把 base 定死」。

**Why:** 实测某集团 2027 校招 559 个岗位里，目标 base 之一为 **0** 个。若按该地硬筛会归零，得出"没有适合岗位"的错误结论。

**How:** 用「base × 适配度」双轴排序。base 命中与异地分开成段，异地单独列出供用户自己判断。

### 3. 输出必须可复核，不能只给结论

每条推荐必须同时给出三样：

- **推荐理由**（逐条对标，写明命中了什么）
- **岗位详情**（JD 原文，不改写、不转述）
- **直达链接**

**Why:** 用户明确要求「除了你帮我做决定，还需要我自己看一下，保证正确性」。只给结论等于让用户盲信。

### 4. 必须交代排除了什么

每份推荐表单列「排除说明」，列出排除数量和主要原因（学历不符 N / 专业不符 N / 职能岗 N / 操作岗 N）。

**禁止静默截断。** 如果只列了 top3，必须写清"共 N 个，此处列前 3"。

### 5. 首选 / 次选必须读 JD 正文，不能只看字段

**专业字段和类别字段都不可靠**，实测三类：

| 陷阱 | 实例 |
|-|-|
| 专业字段写少 | 「研发工程师｜云南驰宏国际锗业」字段仅"冶金工程类"，JD 正文实为"冶金工程类、**化学类、化工与制药类、材料类**、仪器类" |
| 专业字段占位 | 「教师｜山东铝业」字段写"详见职位描述" |
| 类别字段不可靠 | 全站 83 个岗位类别是"不限职位"，导致「采购工程师」「市场营销管理工程师」等职能岗无法靠类别识别 |

**岗位名也会骗人**：「初级循环再生工程师」JD 实为工程项目管理（招标/施工进度/档案）。

**首选 / 次选、异地 Top 3 和「岗位详情」区里的岗位，必须已读 JD。**
其余档位可以只做字段粗筛，但必须在「复核」列标 ⏳，不得写成已核实。

### 6. 简历模板绝对不可修改

生成 PDF **必须严格使用** `references/resume-template.tex`：**只允许在 `\begin{document}` 之后填内容**，
前言层（字体/颜色/间距/宏定义/`\tighten`/CONTENT 注释）**逐字节保留**。

**落地**：内容层单独存 `content.tex`；`resume.tex` = 模板前言层（逐字节复制）+ `content.tex`。
组装后**复核前言层与模板逐字节一致**，不一致就重做。

**Agent 不得改模板**；用户提供新模板时，按第二步 Step 7 的 diff 流程处理。
**Why:** 排版参数是调过的；每次重写会导致不同岗位版式不一致，投递记录看起来零散。

### 7. 审核范围必须等于渲染范围

**用户审核了什么，PDF 里就只能有什么；PDF 里要有的，用户都必须审过。** 两头都成立。

**落地要求：**

1. 「定制简历」= **完整简历文字稿**，不是片段（见第二步 Step 5）。
2. 渲染前**逐条双向对照**：`content.tex` 每句 ↔ 文档每句，不多不少。
3. 任何外部来源（旧简历、模板示例、行业惯例）的内容，必须先写进文档、标明来源、让用户过目，
   **不得在渲染时直接落地**。

**Why:** 用户无法审核他看不到的东西；渲染阶段能自由增删，审核就成了形式。
实测教训：初版把定制简历定义成片段，渲染时从旧简历直接搬了半份简历，一半章节从未进入审核。
**模板示例行（`XXX`、`课程一（90）`、"成果：论文在投"）只是格式占位，必须替换成真实内容。**

### 8. 写入飞书后必须校验格式

**飞书的 markdown 解析器会静默改变格式 —— 不报错、不警告。**

**已知缺陷：相邻加粗会被合并。** 源文件 `**A**普通文字**B**` 写入后变成 `**A普通文字B**`，
加粗跨度吞掉中间的普通文字。实测源文件 100 段加粗，飞书只剩 99 段。

**校验（写完必做）**：

```bash
lark-cli docs +fetch --doc <node_token> --as user --doc-format xml
# 数源文件的 **...** 对数 与 文档的 <b> 段数，必须相等；不等就是被改了
```

**两个坑：**

1. **必须用 `node_token`**（`/wiki/` 链接里那串），不要用 `wiki +node-get` 返回的 `obj_token` ——
   实测后者报 `Invalid document_id`，而同一文档用 node_token 正常。
2. **判断"存储损坏"还是"导出损耗"必须看 XML**；markdown 导出会归一化格式，不能作为依据。

**修复**：把 `**` 按原样写回去会**再次合并**（合并发生在解析时）。
必须**改写结构**（该段只保留一处加粗），并同步改本地 md。
**规避**：同一段避免"加粗 + 普通文字 + 加粗"；宁可少一处粗。

**Why:** 飞书文档是交付物，本地 md 是事实源；格式被静默改动后两者不一致，只能靠主动校验发现。

### 9. 只填不提交

**AI 负责抓取、翻页、填字段；「提交」按钮一律由本人点击。**

**Why:** 网申提交不可撤回，投错岗位、填错字段的代价由用户承担。
且提交是对第三方作出的意思表示，不是可以代劳的操作。

**How:**

- 填完明确告诉用户「已填完，请你核对后自己点提交」，并给出逐条判断留痕
- **不替用户点提交**，也不在用户没明确要求时自动跳到提交页
- 用户已在 ego 浏览器中登录，Skill 不代登录、不碰账号密码

## 浏览器操作（所有步骤通用）：`ego-browser`

**所有网页操作统一走 `ego-browser` CLI**（ego lite 自带 Chromium）。

```bash
ego-browser --version    # 0.6.0.16 / Chromium 154（2026-10-20 实测）
ego-browser skill        # 开工先跑，读它打印的权威用法；API 随版本变化
```

> `command not found` → 用绝对路径 `~/.local/bin/ego-browser`。

**登录态**：ego 是独立浏览器，登录态存在自己的 profile 里，跨会话保留。
**已验证国聘已登录**（个人中心显示实名信息）。其它站点先 `goto` + 观察确认；
**未登录 → `await task.handOff()` 交还用户扫码**，不代登录、不碰账号密码。

### 怎么跑

```bash
ego-browser nodejs <<'EOF'
const task = await taskSpace("<投递目标>-<日期>");   // 一个目标一个 space
const page = task.page("p1");
await page.goto("<岗位链接>");
await page.waitForFunction(() => document.body.innerText.length > 200);
console.log({ spaceId: task.spaceId, page: page.label });
console.log(await page.snapshot());
EOF
```

- **每次调用都是新 Node 进程**，变量不跨轮次：下一轮 `await taskSpace(<spaceId>)` + `task.page("p1")` 接回来。
- **一个目标只建一个 space**，打印并记住 `spaceId`；不要每轮新建，也不要靠"新建 space"绕过卡住的页面。
- **`waitForLoadState()` 只等 load**。React 站点加载完仍是空壳（国聘实测 `innerText` 为 0），
  必须用 `waitForSelector` / `waitForFunction` 等正文出现。
- **收尾**：成功才 `task.finish({ keep: ["p1"] })`；中途交还用户或出错时**不要 finish**。
  整个流程结束前不要 `page.close()`，页面要留给用户回看。

### 操作优先级

1. `page.snapshot()` → 用 `@ref`，或 `loc=role:button[name='...']` / `text=...` 定位
2. `page.click / fill / selectOption / press / hover` —— **真实输入事件**，不是后台 `el.click()`
3. 批量提取、复杂 DOM → `page.evaluate(fn, arg)`（返回值须可 JSON 序列化；页面内读不到 Node 变量）
4. 接口抓数 → `page.fetch(url, opts)`（同源、自动带 cookie）
5. 以上都不够 → `page.cdp(method, params)` 兜底

**常用**：上传 `page.setInputFiles(sel, ["/abs/path"])`；新标签页先 `waitForEvent("popup")` 再点击；
截图 `page.screenshot({ path: "/abs/path.png" })`（绝对路径）；等待用
`waitForSelector / waitForURL / waitForFunction`，别用固定 sleep。

**虚拟滚动**：飞书等 SPA 直接 `scrollIntoView` 会截到空表格。用
`page.evaluate(() => window.scrollBy(0, 600))` 渐进滚动（间隔 ~900ms），等 3~4 秒再截；
或用 `page.snapshot({ scope: "full_page" })`。**截图空 ≠ 没写进去**——先用 `docs +fetch` 回读确认。

# 第一步：岗位检索与推荐表

### Step 1 · 抓取岗位数据

**优先级：找页面自身的 XHR 接口 ≫ DOM 抓取。**

1. 先查 `references/site-adapters.md` —— 已适配站点通常已有现成接口
2. 没有现成接口：`page.cdp("Network.enable")` → `page.reload()` → `await page.events()`，从事件里筛 xhr/fetch
   （**监听必须在 reload 之前开启**，页面加载完再开，日志是空的）
3. 从事件里拿 URL / method / postData，再用 `page.fetch()` 复现一次，确认请求与响应结构
4. 同源分页拉全量：`page.fetch(url, { method, headers, body })`
5. 保存原始数据为 JSON，**保留 `contents`（JD 正文）字段**——后续复核必须用

若找不到接口，退化为 `page.evaluate` 做 DOM 抓取；再不行请用户手工粘贴。

### Step 2 · 归一化

统一为：

```
job_id / title / company / sub_company / location / education
majors[] / headcount / deadline / url / jd_text / category / source_site
```

`sub_company`（二级单位）**必须有**——中铝光叫"工程技术"的岗位就有 8 个，不带二级单位分不清。

### Step 3 · 粗筛（字段 ∪ JD 正文，取并集）

纳入判定 = **平台专业字段命中白名单 ∪ JD 正文命中类目关键词**。

必须取并集而非只信字段——理由是硬规则第 5 条的字段缺陷。

同时剔除：
- 学历不符（低于或高于本人学历层次，如要求大专 / 博士）
- 一线操作岗（优先用平台 `category` 字段；字段缺失或与岗位名冲突时交模型读 JD 判断。**不要手写工种词表**——实测漏了「铸轧工/熔炼工/装配工/压力加工」）

**学历要求写"本科"的岗位要纳入，但单独标注**（校招里"本科"常含硕士，但需用户确认）。

### Step 4 · 读 JD 复核

**首选 / 次选 / 异地 Top 3 必须逐条读 `jd_text` 正文**，判断岗位实质；其余档位可先标 ⏳：

- 是技术/研发岗，还是其实为项目管理、仓储、销售？
- 职能岗（采购/供应链/市场/销售/人力/财务）即便专业命中也不推荐

### Step 5 · 分层排序

**base 命中区**：按优先级 首选 / 次选 / 备选 / 降级 / 不推荐

**异地**：按**专业对口程度**排序，只取 **Top 3**。排序依据见 `references/major-whitelist.md`。

### Step 6 · 生成推荐表

产出《<公司名>-岗位推荐表.md》，**结构与逐节规范见 `references/recommendation-table-format.md`**，
不要另立格式。三条不可省：复核状态三档、筛选方法局限、排除说明。

1. 先落本地 Markdown 给用户过目
2. 用户确认后，在**默认父节点 `EI5owzKRliqQzKkA26PcyjsUnoh`** 下建 `<公司名>` 节点，把推荐表内容写进该节点（用户指定了别的位置才用别处）

**若 `<公司名>` 节点已存在**（之前搜过这家公司），不要新建，**更新该节点内容**，并在表末「变更记录」追加一行。这是第五步「增量更新」的基础。

# 第二步：建档

## 触发

用户在推荐表里选定岗位后（通常是「首选/次选」，也可能包含「备选」）。

**不是每个投递岗位都建档。** 只给用户明确要投的重点岗位建；其余只进 Base 记一行即可。

> **本步是常见的单独入口** —— 用户可能上次已查完岗位，这次直接说「给这个岗位建档」。
> 开工前按「入口」一节问齐输入、查完前置产物，再动手。

### Step 0 · 打开岗位详情页，抓 JD（**建档前必做**）

**建档一开始就用 `ego-browser` 把 `岗位链接` 打开，页面留在该投递目标的 TaskSpace 里。**
（用法见「浏览器操作」一节。）

**Why:** Base 的「备注」只是摘要，会漏掉任职条件、专业类目、截止时间；岗位可能已改版/下架，
**页面才是事实**；页面留着也方便用户回看。

**不同投递方式，页面形态不一样，抓法也不同：**

| 链接指向 | 典型形态 | 怎么抓 |
|-|-|-|
| **招聘平台岗位页**（国聘、智联、BOSS、校招系统）| 结构化「岗位职责 / 任职要求」+ 投递按钮 | 直接抓正文 |
| **企业官网岗位页** | 可能嵌在招聘系统内，或先落在列表页 | 若落在列表页，**先定位到目标岗位**再抓 |
| **高校就业网公告页** | 一篇公告里**含多个岗位** | 抓整篇，**定位到本岗位那一段**；在文档里注明「该公告共 N 个岗位」 |
| **资讯/汇总转载页**（如 `tiku.deizao.cn`、`gaoxiaojob.com`）| 转载，可能残缺 | 抓能抓到的，并**去找官方原始链接**；找不到就说明"转载可能不全" |
| **邮件投递** | 页面只是线索，JD 可能在邮件正文或附件里 | 先抓页面；页面没有 JD → **问用户要** |
| **公众号/微信页** | 可能需要登录或跳转，抓不全 | 能抓就抓；不能 → 让用户复制 JD 发来 |

**抓不到时的铁律：不要用 Base 的「备注」编 JD。** 明确说"页面打不开/需要登录，请把 JD 贴过来"。

**抓完**：把 JD 原文 + 链接 + 抓取时间写进「岗位信息」的「JD 原文」节（**原样粘贴，不转述**），
并在「来源说明」标注来源是"页面实时抓取"还是"用户提供"。

> 若「建档节点」已存在且本次只是补别的东西，可以跳过重抓；但**用户说岗位有更新时必须重抓**。

### Step 1 · 确认前置

- 公司节点 `<默认父节点>/<公司名>/` 是否存在？第①步应该已经建了；不存在则先建：

```bash
lark-cli wiki +node-create --parent-node-token <父节点 node_token> --title "<公司名>"
```

- 推荐表内容是否已写入该公司节点？没有 → 先补写，或确认本次只建档（不要求推荐表）

### Step 2 · 建岗位子节点

```bash
lark-cli wiki +node-create \
  --parent-node-token <公司节点 node_token> \
  --title "<二级单位>-<岗位名>"
```

命名见「飞书写入位置」一节。**二级单位不能省。**

### Step 3 · 建两份文档

在岗位子节点下，依次建：

```bash
lark-cli wiki +node-create --parent-node-token <岗位节点 node_token> --title "岗位信息"
lark-cli wiki +node-create --parent-node-token <岗位节点 node_token> --title "定制简历"
```

模板见 `references/doc-templates.md`。

### Step 4 · 填充「岗位信息」

数据来源：Step 0 从页面抓的 JD（或第①步留存的 JSON）。

- **JD 原文原样粘贴**，不改写、不转述
- **硬性条件对标逐条做**，不确定的标 ⚠️，不要猜
- 加分项没有的写"无"，**不要编**

### Step 5 · 起草「定制简历」（完整简历文字稿）

**个人信息全部来自飞书个人信息库**，实时读取。产出是**简历全文**（页眉、教育、科研、项目、
学生工作、技能、荣誉 —— PDF 里会出现的一切），不是片段。

**只做「选择 + 改写」，不新增事实。** 四条硬约束：

1. 改写过的条目，在文末「改写对照表」列出 **原文 / 改写后 / 改写理由**
2. 「来源说明」逐条列明每章来源；从旧简历/模板示例/外部来源搬来的内容必须标 ⚠️，让用户决定去留
3. **模板示例行是占位符**（如 `成果：论文在投`），不得照抄、不得据此补充
4. 零编造校验：正文所有数字和专有名词都必须能在知识库找到出处

模板与校验细则见 `references/doc-templates.md`。

### Step 6 · 交付用户审核

把两份文档的链接给用户，**明确说明**：

- 哪些内容是原文照搬，哪些是改写
- 有哪些判定标了 ⚠️ 需要其打电话确认
- 有哪些字段因知识库缺失而留空

**用户审核通过后，才进入渲染。** 不要自行认为已经完工。

### Step 7 · 渲染简历 PDF（用户审核通过后才做）

**顺序不可颠倒**：先审文字、再审版式。文字改一行只是改一下，PDF 改一行要重编译一遍。

**模板绝对不可修改**（硬规则第 6 条）。做法：

```
1. 对照校验：content.tex 每句 ↔ 已审核文档每句，双向不多不少
   —— 硬规则 7 的强制关卡，对不上就停，回去改文档并重新让用户审
2. 建岗位目录：简历/<二级单位全称>-<岗位名>/
3. 写内容层 → content.tex（自 \begin{document} 起，至 \end{document}）
4. 复制证件照：`简历/_素材/photo.jpg`（已调好尺寸；不要用 4.3MB 的原图）
5. 组装 resume.tex = 模板前言层（逐字节复制）+ content.tex
6. 复核：前言层与模板逐字节一致，不一致重做
7. 编译两遍：xelatex resume.tex
8. 必查两项：grep -i "missing character" resume.log → 无输出；
   pdfinfo resume.pdf | grep Pages → 1
9. 转图目视：pdftoppm -png -r 130 resume.pdf page && 看图
10. 把 PDF 挂到飞书「定制简历」节点下
```

**上传 PDF 的坑**：替换已有文件时，`--file-token` 原地覆盖会连文件名一起改掉，**必须显式带 `--name`**：

```bash
# 首次上传
lark-cli drive +upload --file resume.pdf --wiki-token <节点> --name "<姓名>-<岗位>-简历.pdf"
# 替换（原地覆盖，保留原链接）
lark-cli drive +upload --file resume.pdf --file-token <file_token> --name "<姓名>-<岗位>-简历.pdf"
```

漏了 `--name` 文件名会变成 `resume.pdf` —— 这个文件名要跟着简历给 HR。补救：
`lark-cli drive +update-title --url "<wiki链接>" --title "<正确文件名>"`。

**模板更新后重渲染**：先 `diff` 新模板与旧 `resume.tex` 的前言层。
- 只有排版层变 → 用新前言层重新组装，`content.tex` 不动，**无需重新审核**（内容没变）
- 宏名/接口变（如 `\skillrow` 参数变了）→ 必须改 `content.tex`，并重新走 Step 6 审核

**超页**：先在内容层开头去掉 `% \tighten` 的注释；仍超则**删条目，不要动排版层**。

**希腊字母必须走数学模式**（`$\delta$`、`$\mu$`），否则拉丁字体无字形，PDF 显示空白但复制正常 —— 极易漏检。

**看完即清**：`page-*.png`、`*.aux`、`*.log`、`*.out` 是过程产物，确认 PDF 无误后删除；
岗位目录只留 `content.tex`、`resume.tex`、`resume.pdf`、`photo.jpg`。

# 第三步：网申表单填报

**红线：AI 只负责填，提交一律由本人点击**（硬规则第 9 条）。

技术手册见 `references/form-filling.md`。本节只讲流程。

> **本步是最常被单独调用的入口** —— 用户经常直接说「帮我填信息」。
> 开工前按「入口」一节问齐输入（**表单链接 · 填哪张表**），再动手。

### Step 1 · 确认前置

- `ego-browser` 可用且目标站点已登录（未登录就 `task.handOff()` 交还本人）
- **岗位申请表**：目标岗位已建档（第二步），「定制简历」已过审
- **简历档案**：只要求飞书个人信息库可达（与具体岗位无关）
- 明确本次填哪张表

### Step 2 · 从飞书取个人信息

**实时读取飞书个人信息库**（地址见文末「指针」）。若有「填表速查卡」这类按表单字段组织的页，**优先用它**。

飞书里没有的字段：先查「待补充清单」；仍没有 → **停下来问本人**，**不得用行业惯例补**。
必填又拿不到数据的处理见 `references/form-filling.md` §4.2。

### Step 3 · 逐板块填报

按站点板块顺序，**填一个保存一个**。通用手法见 `references/form-filling.md`；
站点特有结构见 `references/site-adapters.md` 的「表单填写」。

### Step 4 · 验证

保存后确认编辑器关闭、无字段报错；**全部填完 reload 回读**，核对完成度标记（如国聘「简历目录」）。
**只信回读，不信「点了保存」**。

### Step 5 · 交付用户复核

按 `references/form-filling.md` §4.3 列出逐条判断留痕：选项缺口、单选限制、缺数据取值、未填板块。

### Step 6 · 本人提交

**走到这里就停手**，提交按钮由用户自己点。提交完成后回写 Base（入口 ⑥ Step 7）。

# 入口 ⑥：按投递记录投递

**最常用的一条路。** 用户报一个公司名/二级单位名，Skill 从「投递记录」表里取对应记录，一路推到"待你点提交"。

## 输入

用户主动报**公司名或二级单位名**（岗位名可选；待投记录通常没有 `岗位名称`）；AI 用它去 Base 查，**不要列出全表让用户挑**。
其余从 Base 读，不要再问岗位链接。定位后按 Step 2 确认一次方向（只确认是否直接投，不是从表里挑记录）。

## Step 1 · 定位记录

用「与 Base 的分工」里的 `+record-search` 命令，`--keyword "<公司名或二级单位名>"` 查询
（search-field 覆盖 `公司` / `岗位名称` / `备注` 三列；**待投记录的 `岗位名称` 为空是正常的**，定位以公司或备注里的二级单位为准）。
返回是矩阵：`data.fields` 是列名，`data.data` 是行，`data.record_id_list` 是每行对应的 record_id。

**用户给公司名/二级单位名，AI 自己查、自己定 —— 不要用选择器（包括 AskUserQuestion）、不要贴全表让用户挑。**

选取顺序：
1. 先按返回的 `公司` 与 `备注` 过滤，再做包含匹配（公司全称/简称互相包含；二级单位名在 `备注` 里匹配）；`岗位名称` 只在已投记录里有值，**不能用来识别待投记录**；**不要仅凭 keyword 命中就用**
2. 多条候选 → 优先 `投递状态` 包含「待投」的
3. 仍多条 → `截止日期` 有值的优先，取最近且未过期的；为空就看 `备注` 里的日期
4. 仍多条 → 取返回顺序的第一条，并在告知里说明
5. 选中后**明确告知**：「我取的是 <公司> · <岗位>（待投，截止 X）；要换直接说岗位名。」
   **待投记录的 `岗位名称` 为空是正常的**：用 `岗位链接` / `备注` 指代，不要编岗位名，也不要为了这句话提前写 Base。

**查不到** → 说"表里没有这家公司"，问是否新增一条或从岗位搜集开始；新增待投记录时 `岗位名称` 留空；**不要贴全表**。

search 结果不准时，可用 `+record-list` 在内部过滤，但**仍然不要贴给用户**。

## Step 2 · 先问方向（**必做，不得跳过**）

**记录已由 AI 选好；这里只问方向，不要再让用户从表里挑记录。**
**定位到记录后不要直接开投，先问：**

> 找到「<公司> · <岗位>」（状态 / 截止 / 建档：未建或已建）
>
> **A. 直接投这个岗位** —— 用记录里的信息走建档 + 填报
> **B. 从岗位搜集重新开始** —— 重新抓这家公司的秋招岗位，筛一遍再决定

**`岗位名称` 为空时**，用 `岗位链接` / `备注` 里的岗位信息代替，不要凭空补岗位名（投递前本来就不该有值）。

**为什么必须问**：记录可能是几天前攒的，岗位可能已下架、要求变了，或公司又放了新岗位。
直接开投等于把"当时的一个判断"当成"现在的结论"。**即使他说"投 XX 那个岗位"，也要问** —— 说法只代表倾向。

**选 B**：转入第一步重新抓岗位、出推荐表；完成后让用户从新推荐表里报岗位名，**不要沿用原记录**。

## Step 3 · 读出并核对

记录里这些字段决定了后面怎么走：

| 字段 | 用途 |
|-|-|
| `公司` | 定位（用公司全称/简称匹配）|
| `岗位名称` | **投递前为空**；投递完成后才回填最终岗位，不能拿它反推待投岗位 |
| `岗位链接` | 投递入口（**先判断类型，见 Step 4**）|
| `备注` | **常含二级单位、行动指令、投递邮箱、命名规则、专业要求、薪资** —— 必须读 |
| `建档节点` | 有 → 跳过建档；空 → 先建档 |
| `投递状态` | 不是「待投」→ 先提醒：这条已经投过了，确定重投？ |
| `截止日期` | 已过期 → 提醒 |

> Base 没有独立的 `二级单位` 列；建档命名所需的二级单位全称从 `备注` 读。

## Step 4 · 打开岗位页 + 判断投递方式（关键）

**用 `ego-browser` 打开 `岗位链接` 并留在 TaskSpace 里；再判断投递方式。不要凭 URL 猜。**

| 类型 | 识别特征 | 怎么处理 |
|-|-|-|
| **网页网申表单** | 国聘、公司官网、校招系统（如 `c.iguopin.com`、`zhiye.com`）| 浏览器操作填表，走「第三步：网申表单填报」|
| **邮箱投递** | `备注` 里出现邮箱（`xxx@xxx.com`）+ "邮件标题"之类 | **不代发**。从备注里抽出：收件人、邮件主题、需要附的材料 → 列给用户，由他本人发送 |
| **公众号 / 二维码** | `备注` 写"关注 XX 公众号" | 只能用户手机操作。把要点整理给他 |
| **信息页而非投递页** | 高校就业网公告、资讯站、岗位汇总页 | 先从页面里找到**真正的投递入口**（往往在文末），找不到就问用户 |

打开后顺手抓 JD（建档要用）；页面打不开（需登录/已下架/公众号限制）→ **当场告诉用户**，别拖到建档。

## Step 5 · 建档（若「建档节点」为空）

走第二步全套（Step 0 的页面已在 Step 4 打开，直接复用；含岗位信息 + 定制简历 + 渲染 PDF）。
用户从入口 ⑥ 明确选中的岗位，**视为重点岗位**，可以建档。Base 的「备注」只是摘要，**不能当 JD 用**。

## Step 6 · 投递

按 Step 4 判定的方式走。**网页表单**走「第三步：网申表单填报」。

## Step 7 · 回写 Base（必做）

**必须等用户明确说「已提交」**（或已发出邮件），再更新该行；不要填完就标记已投。

| 字段 | 更新为 |
|-|-|
| `投递状态` | `已投` |
| `投递日期` | 当天 |
| `岗位名称` | **最终实际投递的岗位名称**（以实际提交的岗位 / 投递完成页为准，邮件投递以邮件里的岗位为准；投递前保持为空）|
| `备注` | 用户给出的后续动作（等笔试 / 等回复）；**追加**到原备注，不要覆盖 |
| `建档节点` | 若本次新建了，回填节点链接 |

> `岗位名称` 必须与 `投递状态`、`投递日期` **同一次回写**，不要提前写。若实际投递的岗位与记录里的 `岗位链接` / `备注` 不一致，写**实际投递的岗位**，并在 `备注` 里补一句差异。

```bash
lark-cli base +record-batch-update --base-token EGkqbFQmkauCe4sqdJOcKmWon4T \
  --table-id tblPKAEr1fsJ3oSm --as user --json \
  '{"update_records":{"recXXX":{"投递状态":["已投"],"投递日期":"<当天 YYYY-MM-DD>","岗位名称":"<最终实际投递的岗位名称>"}}}'
```

**没回写就等于没投** —— 下次用户看表还是「待投」，会重复投；`岗位名称` 也会一直空着。
